# brain_fast 폴더 구조 가이드 (초보자용)

이 문서는 “어디에 어떤 코드를 넣어야 하는지”를 팀원이 쉽게 구분할 수 있게 만든 설명입니다.

---

## 1. 이 프로젝트가 하는 일 (한 줄)

웹/앱에서 요청이 들어오면 → 서버가 처리하고 → DB에 저장하거나 → 화면(HTML)을 보여주는 FastAPI 프로젝트입니다.

---

## 2. 요청이 흐르는 순서 (가장 중요)

브라우저/앱에서 요청이 오면 보통 아래 순서로 코드가 실행됩니다.

1. routers/        ← “이 주소로 들어왔다” (문지기)
2. schemas/        ← “들어온 데이터 형식이 맞나?” (검사표)
3. services/       ← “실제로 무슨 일을 할까?” (업무 처리)
4. repositories/   ← “DB에 저장/조회할까?” (창고 관리)
5. models/         ← “DB 테이블 구조는?” (설계도)

화면에 보여줄 때는:

- templates/  ← HTML 뼈대
- assets/     ← CSS/JS/이미지 (꾸미기 + 동작)

비유:

- routers = 은행 창구 안내
- services = 은행 직원
- repositories = 금고/창고 담당
- models = 금고 선반 설계도
- schemas = 서류 양식 검사
- templates/assets = 손님에게 보이는 안내판/인테리어

---

## 3. 폴더별 상세 설명

### 📁 routers/

**역할:** URL(주소)과 연결되는 “입구” 코드

**여기에는 뭘 넣나요?**

- `/admin/...`, `/api/...` 같은 주소 정의
- 요청을 받아서 service로 넘기는 코드
- 로그인 후 페이지 이동, 파일 업로드 받기 등

**여기에는 넣지 마세요**

- 복잡한 계산/업무 로직 (→ services)
- DB 직접 조회/저장 (→ repositories)

**현재 파일**

- `admin.py` : 관리자 웹페이지 관련 주소 (`/admin`)
- `brain.py` : 뇌/화면공유 ROI 분석 API
- `commonness.py` : 일반 API (로그인, Q&A, 학습 등 JSON API)

**언제 여기를 수정하나요?**

- 새 API 주소를 만들 때
- 관리자 페이지 새 메뉴 URL을 추가할 때

---

### 📁 services/

**역할:** 실제 “업무”를 처리하는 핵심 로직

**여기에는 뭘 넣나요?**

- “로그인 가능한지 확인”
- “Q&A 답변 저장”
- “스터디 생성/수정”
- “팝업 노출 조건 계산”
  같은 비즈니스 규칙

**여기에는 넣지 마세요**

- URL 정의 (→ routers)
- SQL/DB 세세한 조회문 (→ repositories)

**현재 파일 예시**

- `userServices.py` : 사용자 관련
- `qaServices.py` : Q&A 관련
- `studyServices.py` : 스터디 관련
- `popupServices.py` : 팝업 관련
- `learningServices.py` : 학습 관련
- `reviewNodeServices.py` : 복습 노드 관련
- `roiGradeServices.py` : ROI 등급 관련
- `nasServices.py` : NAS(파일 저장소) 관련
- `dashboardServices.py` : 대시보드 관련

**언제 여기를 수정하나요?**

- “기능이 어떻게 동작해야 하는지”를 바꿀 때

---

### 📁 repositories/

**역할:** DB와 직접 대화하는 코드 (조회/추가/수정/삭제)

**여기에는 뭘 넣나요?**

- “유저 찾기”
- “Q&A 목록 가져오기”
- “스터디 저장하기”
  같은 DB 작업

**여기에는 넣지 마세요**

- 화면 표시 로직
- 복잡한 업무 판단 (가능하면 services에서)

**현재 파일 예시**

- `userRepositories.py`
- `qaRepositories.py`
- `studyRepositories.py`
- `popupRepositories.py`
- `learningRepositories.py`
- `reviewNodeRepositories.py`

**언제 여기를 수정하나요?**

- DB에서 데이터를 어떻게 가져올지/저장할지 바꿀 때

---

### 📁 models/

**역할:** DB 테이블 구조를 파이썬 클래스로 정의

**여기에는 뭘 넣나요?**

- 테이블 이름, 컬럼(이름/타입), 관계 정의

**주의**

- models는 “테이블 설계도”입니다.
- 여기에 긴 업무 로직을 넣지 않습니다.

**현재 파일 예시**

- `userModel.py` : 사용자 테이블
- `qaModel.py` : Q&A 테이블
- `studyModel.py` : 스터디 테이블
- `popupModel.py` : 팝업 테이블
- `reviewNodeModel.py` : 복습 노드 테이블
- `medicalTermsModel.py` : 의학 용어 테이블

**언제 여기를 수정하나요?**

- DB에 새 컬럼/테이블이 필요할 때

---

### 📁 schemas/

**역할:** API로 주고받는 데이터 형식(검증) 정의

**여기에는 뭘 넣나요?**

- 요청 body 형식 (예: 로그인 시 email/password 필수)
- 응답 형식 (예: 반환할 필드 목록)
- 값이 잘못되면 422 에러로 막아줌

**현재 파일 예시**

- `userSchemas.py`
- `qaSchemas.py`
- `studySchemas.py`
- `popupSchemas.py`
- `analyzeSchemas.py` (분석 API용)

**언제 여기를 수정하나요?**

- API 입출력 필드가 바뀔 때
- “이 값은 반드시 있어야 한다” 규칙을 추가할 때

---

### 📁 templates/

**역할:** 서버가 만들어주는 HTML 화면

**여기에는 뭘 넣나요?**

- 관리자 페이지 HTML
- 로그인/목록/상세 화면 HTML

**현재 구조**

- `templates/admin/` : 관리자 페이지들
  - `login.html`, `user.html`, `qa.html`, `study.html`, `popup.html` 등
  - `partials/layout_adm.html` : 관리자 공통 레이아웃(헤더/사이드바 등)
- `templates/screen_analyze.html` : 화면 분석 관련 페이지

**언제 여기를 수정하나요?**

- 화면에 보이는 글자/버튼/레이아웃(HTML)을 바꿀 때

---

### 📁 assets/

**역할:** 프론트 정적 파일 (CSS/JS/이미지/폰트)

**하위 폴더**

- `css/` : 스타일 (색, 간격, 레이아웃)
- `js/` : 화면 동작 스크립트
  - `js/admin/` : 관리자 페이지용 JS
  - `js/common/` : 공통 JS
  - `js/datatables/` : 표(테이블) 관련
- `img/` : 이미지
- `fonts/` : 폰트
- `demo/` : 데모용 리소스

**언제 여기를 수정하나요?**

- 디자인/애니메이션/버튼 클릭 동작(프론트)을 바꿀 때

---

### 📁 utils/

**역할:** 여러 기능에서 공통으로 쓰는 도우미 코드

**현재 파일 예시**

- `adminAuth.py` : 관리자 로그인/권한 확인
- `password.py` : 비밀번호 해시/검증
- `renderHelper.py` : 템플릿 렌더 도우미
- `qa_sse.py`, `review_sse.py`, `study_sse.py`, `user_sse.py` : 실시간 알림(SSE)

**언제 여기를 수정하나요?**

- 여러 service/router에서 반복해서 쓰는 공통 기능이 필요할 때

---

### 📁 class/

**역할:** 뇌영상/ROI 분석 같은 전문 로직(AI·전처리 등)

**현재 구조**

- `class/brain/`
  - `preprocess.py` : 전처리
  - `ensemble.py` : 모델 앙상블
  - `medgemma.py` : 모델 관련
  - `localization.py` : 위치 추정
  - `report_format.py` : 결과 리포트 포맷
  - `constants.py`, `config.py` : 상수/설정

**언제 여기를 수정하나요?**

- 분석 알고리즘/모델 관련 코드를 건드릴 때
  (일반 CRUD 기능은 보통 여기가 아님)

---

### 📁 docker/

**역할:** Docker로 서버/DB를 실행할 때 쓰는 설정

**포함 내용**

- 앱 시작 스크립트
- PostgreSQL Dockerfile
- DB 초기화 SQL (`postgres/init/03_qa.sql` 등)

**언제 여기를 수정하나요?**

- 로컬/배포 환경을 컨테이너로 맞출 때
- DB 초기 테이블/시드 데이터를 컨테이너 기준으로 넣을 때

---

### 📁 docs/

**역할:** 기획/설계 문서와 다이어그램

**예시**

- `screen_flow.png` : 화면 흐름
- `usecase_diagram.png` : 유스케이스 다이어그램
- `_build_srs.py` : 요구사항 문서 생성 관련 스크립트
- `폴더구조_초보자가이드.md` : 이 문서

**언제 여기를 보나요?**

- “이 기능이 왜 있는지/화면이 어떻게 흘러가는지” 확인할 때

---

### 📁 tests/

**역할:** 자동 테스트 코드

**예시**

- `test_log_retention.py` : 로그 보관/삭제 동작 테스트

**언제 여기를 수정하나요?**

- 기능을 만든 뒤 “진짜 잘 되는지” 자동 검증을 추가할 때

---

### 📁 logs/

**역할:** 서버 실행 중 생긴 로그 저장소 (날짜별)

**특징**

- `logs/YYYY-MM-DD/` 형태로 쌓임
- 보통 직접 수정하지 않음 (읽기만)

**언제 여기를 보나요?**

- 에러가 났을 때 원인 확인할 때

---

## 4. 루트(최상위) 주요 파일

- `main.py`
  - 서버 시작점. 라우터 연결, 미들웨어, 로그 정리 등

- `config.py`
  - 환경설정 (.env 값 읽기, DB 주소 등)

- `db.py`
  - DB 연결/세션 생성

- `exception_handlers.py`
  - 에러가 났을 때 사용자 응답 + 로그 남기기

- `logging_setup.py`
  - 로그 파일 위치/보관 기간 설정

- `requirements.txt`
  - 필요한 파이썬 패키지 목록

- `docker-compose.yml`, `Dockerfile`
  - 컨테이너로 앱/DB 실행하는 설정

- `.env` / `.env.example`
  - 실제 비밀설정 / 설정 예시
  - `.env`는 절대 깃허브에 올리지 않기

---

## 5. 보통 건드리지 않는 폴더

- `.venv/` : 파이썬 가상환경 (라이브러리 설치 공간)
- `.git/` : 버전 관리 내부 데이터
- `.idea/` : IDE 설정
- `__pycache__/` : 파이썬 자동 생성 캐시

→ 이 폴더들은 기능 개발할 때 직접 수정하지 않습니다.

---

## 6. “어디에 코드를 넣지?” 빠른 판단표

| 하고 싶은 일 | 넣을 곳 |
|---|---|
| 새 URL/API 주소 만들기 | `routers/` |
| 기능 동작 규칙 만들기 | `services/` |
| DB 조회/저장 만들기 | `repositories/` |
| DB 테이블/컬럼 추가 | `models/` (+ 필요시 SQL/마이그레이션) |
| 요청/응답 데이터 형식 정하기 | `schemas/` |
| 관리자 HTML 화면 수정 | `templates/admin/` |
| 버튼 동작/디자인 수정 | `assets/js/`, `assets/css/` |
| 공통 유틸(비밀번호, 권한 등) | `utils/` |
| 분석 모델/전처리 수정 | `class/brain/` |
| Docker/DB 초기설정 | `docker/` |
| 테스트 추가 | `tests/` |

---

## 7. 기능 하나 추가할 때 추천 순서 (실무)

예: “Q&A에 새 필드 추가”

1. `models/` : DB 컬럼 추가
2. `schemas/` : API 입출력 형식 추가
3. `repositories/` : DB 저장/조회 반영
4. `services/` : 업무 로직 반영
5. `routers/` : API/페이지에서 연결
6. `templates/` + `assets/` : 화면에 보이게/동작하게
7. (가능하면) `tests/` : 테스트 추가

---

## 8. 팀 협업 규칙 (초보 추천)

1. 한 기능은 가능하면 위 레이어 순서를 지킨다.
2. router에 DB 코드를 직접 길게 쓰지 않는다.
3. service에 HTML/CSS를 넣지 않는다.
4. 파일을 새로 만들 때 이름 규칙을 맞춘다.
   - 예: `xxxServices.py`, `xxxRepositories.py`, `xxxModel.py`, `xxxSchemas.py`
5. 잘 모르겠으면 “이 코드가 URL인지 / 업무인지 / DB인지 / 화면인지”만 먼저 말하고 팀원에게 위치를 확인한다.

---

## 9. 한 문장 암기

> routers는 입구, services는 일 처리, repositories는 DB, models는 테이블, schemas는 데이터 검사, templates/assets는 화면.
