아이디·비밀번호 찾기

메일을 보내지 않고 가입 정보가 일치하는지 확인한다. 이름·생년월일은 계정 소유를 증명하는 인증수단과 다르다. 이 기능은 기존 회원 테이블을 쓰며 새 테이블을 만들지 않는다.

요청이 지나가는 순서

화면은 학습자 Vue 프로젝트의 /find(FindAccountPage.vue)가 맡고, 이 서버는 API만 둔다. 화면 입력 → Vue의 POST 요청 → 라우터 → 입력 스키마 → 서비스 → 레포지토리 → 회원 DB. 응답은 같은 경로를 거꾸로 돌아와 화면에 표시된다.

주소받는 값처리·반환
POST /find-iduser_name, user_birth삭제되지 않은 일치 회원의 아이디를 일부 가려서(예: le***@example.com) user_ids로 반환. 한 명이면 user_id도 반환
POST /find-pw/verifyuser_id, user_name, user_birth, answers(질문 답 3개)신원과 답 3개가 모두 맞으면 ok. 틀린 항목이 무엇인지 알려 주지 않고 같은 404 문구를 쓴다
POST /find-pw가입 정보 3개, answers, user_pw, user_pw_confirm회원 행을 잠근 뒤 신원·답을 다시 확인하고 새 비밀번호 bcrypt 해시 저장

파일별 역할

파일받는 것 → 하는 일 → 돌려주는 것
schemas/accountSchemas.pyJSON → 이름·날짜·길이 검사 → 검증된 객체. 회원 존재 여부는 확인하지 않는다.
routers/account.pyHTTP 요청 → 서비스 호출 → JSON. SQL을 작성하지 않는다.
services/accountServices.py객체·DB 세션·접속 IP → 시도 횟수 확인, 아이디 가리기, 확인·비밀번호 해시·커밋 → 성공 여부. HTML을 생성하지 않는다.
utils/rate_limit.py키(IP, 아이디 등) → 최근 10분 시도 횟수 계산 → 허용 여부. 서버 메모리에만 저장하므로 재시작하면 초기화되고 워커끼리 공유하지 않는다.
repositories/accountRepositories.py조회 조건·해시 → user_member 조회·수정 → 회원/아이디. 평문 비밀번호를 저장하지 않는다.

헷갈리기 쉬운 점

  • 첫 확인에서 성공했어도 변경 API는 가입 정보를 다시 확인한다. 입력란을 숨기는 것만으로 변경을 허용하지 않는다.
  • 동명이인·동일 생년월일이면 아이디를 한 개로 추측하지 않고 목록으로 반환한다.
  • del_yn=Y인 회원은 찾기와 변경에서 제외한다.
  • 아이디는 이메일이라 이름·생년월일만으로 전체를 보여주면 개인정보가 드러난다. 그래서 앞 두 글자만 남기고 가린다. 가려진 아이디로는 재설정할 수 없으므로, 재설정 탭에서는 아이디를 직접 입력한다.
  • 세 API를 합쳐 IP당 10분에 30회, 같은 계정(아이디 또는 이름+생년월일)당 10분에 5회까지 허용한다. 넘으면 429를 돌려준다. 제한에 걸린 동안에는 맞는 정보를 넣어도 막힌다.
  • 프록시(nginx 등) 뒤에서 돌리면 모든 요청의 IP가 프록시 주소로 보일 수 있다. 이때는 IP 제한이 전체 사용자에게 함께 걸리므로 프록시 설정을 확인해야 한다.
  • 비밀번호는 기존 회원 규칙에 맞춰 4자 이상이며 bcrypt의 UTF-8 72바이트 제한을 지킨다. 앞뒤 공백을 제거하지 않는다.
  • 422는 입력 형식 오류, 404는 가입 정보 불일치, 400은 비밀번호 불일치, 429는 시도 횟수 초과다. 오류 응답에 입력한 비밀번호를 넣지 않는다.

마이페이지 본인 조회(GET /me)와 로그아웃(POST /logout)

무엇을 하나. 일반 로그인한 학습자가 마이페이지에서 내 프로필(아이디·이름·학교·전공)과 최근 저장된 문제 제출 5건을 본다. 로그아웃은 이 브라우저의 학습자 로그인을 서버에서 끝낸다.

어느 파일인가. routers/user.py의 GET /me, routers/account.py의 POST /logout, services/accountProfileServices.py(세션 확인·표시용 값 만들기), repositories/accountProfileRepositories.py(본인·최신 5건 읽기), schemas/accountProfileSchemas.py(허용 필드만).

동작 순서. 요청 → 서버 세션의 learner만 보고 회원을 정한다(요청이 낸 번호·쿼리는 쓰지 않는다. user_idx·idx·user_id 쿼리는 400) → 활성 회원을 다시 읽는다(세션 없음·형식 오류·탈퇴·없는 회원·관리자 세션만·게스트는 401, 관리자 승인 표시가 아니면 403) → 제출은 review_node에서 본인·삭제 안 된 제출·문제가 있는 제출만 저장 시각 최신 순(같으면 번호 큰 순)으로 SQL에서 5건만 읽는다 → 비밀번호·해시·생년월일·영상 주소·병명·기준 박스는 응답에 넣지 않는다. 모든 응답은 Cache-Control: no-store이고 DB에 쓰지 않는다. 로그아웃은 Origin이 이 서버의 Host/scheme와 같고 Sec-Fetch-Site가 cross-site가 아닐 때만 session["learner"]를 지운다(관리자 세션·게스트 쿠키는 그대로).

확인하는 법. tests/test_account_me.py(권한 경계·허용 필드·최근 5건 규칙·no-store·쓰기 0·로그아웃 출처 검사·계정 API 예상 못한 오류에서 입력값이 응답·로그에 새지 않는지)를 실행한다. 한계: 서명 쿠키 방식이라 다른 브라우저·이미 복사된 쿠키까지 끄는 전역 폐기가 아니고, 시도 횟수 제한은 서버 메모리라 재시작·여러 worker에서는 공유되지 않는다.

마이페이지 학습 통계(GET /me/stats)

무엇을 하나. 마이페이지(시안 B)의 푼 문제 수·정답률·이번 주 푼 문제·연속 학습일·최근 7일 학습량·부위별 정답률을 본인 저장 기록으로 계산해 준다. 읽기만 하며 DB 칸·인덱스·영상·모델을 건드리지 않는다.

어느 파일인가. routers/user.py의 GET /me/stats, services/accountStatsServices.py(인증 재사용·시계 정책·응답 만들기), repositories/accountStatsRepositories.py(집계 SQL 한 문장), schemas/accountStatsSchemas.py(허용 필드·합계·범위 검증).

동작 순서. GET /me와 같은 인증(서버 세션 learner만, 회원 선택 쿼리는 400, 401/403) → 집계 SELECT 한 번 → 응답. 집계는 본인·삭제 안 된 제출·문제 번호가 있는 제출 중 채점 결과가 C/H/W인 것만 쓴다(다른 값은 오답으로 바꾸지 않고 '채점되지 않은 제출'로만 센다). 푼 문제 수와 정답률은 문제별 마지막 채점 한 건으로 계산하고(부분정답은 분모에 넣고 정답에서는 제외), 이번 주·최근 7일·연속 학습일은 모든 채점 제출에서 날짜별로 서로 다른 문제를 세고, 연속 학습일은 하루 목표(services/accountStatsServices.py의 DAILY_GOAL, 현재 5문제) 이상 푼 날만 학습일로 친다(요청으로 바꿀 수 없다). 부위는 현재 문제 정보로만 나누고 삭제·잘못된 부위는 '부위 미확인'으로 따로 센다.

날짜 기준(중요). 저장 시각(created_at)은 시간대가 없는 값이다. 사용자 결정(2026-11-06)으로 한국 시간(Asia/Seoul)으로 읽는다(저장된 시각에 +9시간을 더하지 않는다). 이 결정은 실DB 저장 시계를 읽기 전용으로 확인한 결과가 아니다(실DB 조회 0). 실제 값이 UTC로 밝혀지면 services/accountStatsServices.py의 SOURCE_TIMEZONE을 'UTC'로 바꾼다. SOURCE_TIMEZONE이 None(시계 미확인)이면 날짜 숫자(연속일·이번 주·7일·요일)를 null로 주고 calendar.status=unavailable로 표시하며 총계·정답률·부위는 실제 값을 준다(시험이 주입하는 폴백). 채점 기록이 0건이면 해석할 시각이 없으므로 0으로 정직하게 준다. 변환은 DB 시간대 이름이 아니라 고정 시간 이동(서울=+0, UTC=+9)으로 해서 DB의 시간대 데이터에 기대지 않는다.

확인하는 법. tests/test_account_stats.py(임시 내장 PostgreSQL, 고정 예제·시계 정책·경계·권한·읽기 전용·응답 형식)와 tests/test_account_stats_perf.py(합성 10만 건 성능)를 실행한다. 한계: 기존 공용 제출 경로가 믿는 입력의 한계는 통계가 해결하지 않고, 과거에 삭제·누락된 기록은 복구할 수 없으며, 실DB의 저장 시계와 인덱스는 이번에 확인하지 않았다.

마이페이지 정보 수정·비밀번호 변경(GET /me/settings, PATCH /me/profile, POST /me/password)

무엇을 하나. 일반 로그인한 학습자가 이름·학교·전공을 고치고 비밀번호를 바꾼다. 아이디·생년월일·권한·승인/탈퇴 표시는 바꾸지 않는다. 탈퇴와 복구(비밀번호 찾기) 변경은 이 구현에 없다.

어느 파일인가. routers/accountSettings.py(인증·출처 검사·오류 변환, routers/user.py가 include), services/accountSettingsServices.py(회원 행 잠금·충돌 버전·현재 비밀번호 확인·시도 제한), repositories/accountSettingsRepositories.py(쓰기 칼럼 고정), schemas/accountSettingsSchemas.py(허용 필드·길이·제어문자). 관리자용 update_user는 재사용하지 않는다.

동작 순서. 쓰기(PATCH/POST)는 로그아웃과 같은 같은 출처(Origin) 검사(+ Origin에 경로가 붙어 있으면 거절)를 먼저 한다 → 서버 세션 learner로만 회원을 정한다(회원 선택 쿼리는 400, 401/403) → 승인된 회원별 5회·IP별 30회/10분 시도 제한(틀린 비밀번호도 소모, 성공해도 초기화 없음, 프로필·비밀번호 공통) → 회원 행을 FOR UPDATE로 잠그고 최신 값으로 다시 읽은 뒤 충돌 버전 확인(409) → 현재 비밀번호를 지금 DB 해시로 확인(400) → 쓰기 → commit(실패는 rollback). 프로필 수정은 user_name·user_un·user_sp·updated_at만, 비밀번호 변경은 user_pw·updated_at만 쓴다. 비밀번호 변경이 성공하면 이 요청의 learner 세션 키만 제거한다(관리자 세션·게스트·다른 기기는 그대로, 전역 폐기 아님). 충돌 확인용 profile_version은 세션 서명 비밀로 만든 불투명 HMAC이라 새 DB 칸이 필요 없다.

확인하는 법. tests/test_account_settings.py(임시 내장 PostgreSQL: 권한·출처 매트릭스·허용 필드/칼럼·충돌·동시 요청·시도 제한·롤백·입력 비반사)를 실행한다. 한계: 서명 쿠키라 다른 기기의 로그인은 끝나지 않고(R03), 시도 제한은 서버 메모리라 재시작·여러 worker에서 공유되지 않는다(R04). 이름·학교·전공이 복구 확인에 쓰일 수 있다는 점은 복구 방식 선택 뒤 별도 반영한다.

비밀번호 찾기 질문(복구 B안)

가입할 때 고정 질문 3개(Q01 처음 다닌 초등학교 이름, Q02 어릴 때 사용하던 별명, Q03 어릴 때 살았던 동네 이름)의 답을 함께 받는다. 답은 평문으로 저장하지 않는다. 정규화(answer_norm_v1: NFC → 앞뒤 공백 제거 → 연속 공백 1개 → 영문 대문자만 소문자) 뒤 답마다 bcrypt 해시를 새 테이블 user_recovery_answer 에 넣는다.

주소하는 일
POST /signup기존 6필드 + recovery_answers 3개. 회원과 답 3행을 한 트랜잭션으로 저장(부분 저장 없음). 이미 있는 아이디는 409
GET /me/recovery-questions로그인한 학습자의 등록 여부만(답·해시는 주지 않음)
PUT /me/recovery-questions현재 비밀번호 + 답 3개로 최초 등록·변경. 같은 출처 검사·시도 제한(정보 수정과 공유)
  • 답이 들어가는 4개 주소는 routers/accountSafeErrors.py 의 route 클래스를 쓴다. 422 는 정해 둔 위치(loc)와 고정 코드(code)만 돌려주고, 입력 값·보낸 키 이름·서버 문구는 응답과 로그에 넣지 않는다.
  • 답 확인은 회원이 없거나 답을 등록하지 않았어도 bcrypt 검증을 3번 한다(미리 만든 더미 해시 사용). 시도 제한에 걸리면 bcrypt 를 하지 않는다.
  • 프로세스 환경 변수 ACCOUNT_RECOVERY_MAINTENANCE=1 이면 가입·비밀번호 찾기·질문 등록 주소가 DB·bcrypt 전에 503 을 준다(전환·장애 때 서버에서 막는 스위치).
  • 테이블 DDL 은 docker/postgres/user_recovery_answer.sql(자동 실행되지 않는 수동 파일). 공유 DB 에 넣기 전에는 사전 스키마 대조 도구로 없음/일치/불일치를 먼저 확인한다. 같은 트랜잭션에서 RLS 를 켜고(정책 0개) PUBLIC·anon·authenticated 권한을 회수한다. Supabase 의 일반 API 로는 이 표를 읽거나 쓸 수 없고, 표 소유자인 백엔드 역할만 쓴다. 그래서 DDL 은 백엔드가 접속하는 역할로 실행해야 한다.
  • 답 미등록 회원은 비밀번호 찾기를 할 수 없다(로그인한 뒤 설정에서 등록, 잊었으면 관리자 문의).

남은 문제

질문 답은 추측·검색될 수 있어 강한 본인 인증이 아니다(지식 기반 복구의 한계). 발표용으로 운영하지 않는다는 전제의 선택이다.

검증

python -m pytest tests/test_account_recovery.py tests/test_account_recovery_questions.py tests/test_learner_signup_answers.py -q 는 임시 DB(SQLite·내장 PostgreSQL)에 가상 회원·답을 만들어 API·잠금·비반사·점검 차단을 확인한다. 운영 PostgreSQL 연결 확인은 별도로 필요하다.
