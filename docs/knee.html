무릎 MRI 분석은 무엇을 하는가

무릎 MRI 볼륨(슬라이스 묶음)을 받아 “이상 소견”, “ACL(전방십자인대)”, “반월판” 세 가지를 숫자로 추정하고, ACL이 있는 대략적인 위치를 박스로, 모델이 참고한 영역을 색으로 보여 줍니다. 의사 진단이 아닙니다.

결과는 학습·실습용 보조입니다. 박스는 “ACL이 있는 대략적 해부학 위치”이고 파열 위치가 아닙니다. 색 영역은 모델이 참고한 곳이지 병변이 아닙니다. 숫자는 보정된 모델 점수이지 개인의 실제 위험률이 아닙니다.

두 가지 방법으로 쓸 수 있습니다. ① 볼륨 분석: 코드로 knee_service.predict(...)를 직접 부르는 방식(주소는 아직 없음). ② 화면 캡처 한 장 분석: POST /api/v1/knee/screen-roi. 아래 “화면 캡처 한 장 분석” 절을 보세요.

중요: 한 장으로 분석하는 방식은 아직 검증되지 않아, 지금은 모든 소견이 “평가하지 않음”으로 나오는 것이 정상입니다.

한 번 예측이 지나가는 순서

  1. 호출하는 쪽이 촬영면별 볼륨을 {"axial": ..., "coronal": ..., "sagittal": ...} 모양으로 넘깁니다. 일부 면만 있어도 됩니다.
  2. preprocess.py가 볼륨이 (슬라이스, 높이, 너비) 숫자 배열인지, NaN·너무 큰 크기가 아닌지 확인합니다. 이상하면 여기서 멈춥니다.
  3. ensemble.py가 소견마다 필요한 촬영면 모델로 확률을 구해 평균하고 보정합니다.
  4. 보정된 확률이 0.4~0.6 사이면 “판단 어려움”, 아니면 “가능성 높음/낮음”으로 문구를 정합니다.
  5. 필요하면 localization.py가 ACL 박스와 Grad-CAM 색 영역을 만듭니다.

class/knee/ensemble.py — 앙상블

한 줄
가중치를 받아 오고, 촬영면별 예측을 합쳐 소견별 결과를 만듭니다.
받는 것
촬영면 이름을 키로 한 볼륨 묶음. 예: {"sagittal": 볼륨}.
하는 일
처음 부를 때 load()로 Hugging Face에서 파일 17개를 받아 모델 14개를 올립니다. 예측 때는 소견마다 필요한 촬영면의 확률을 평균하고, 보정한 뒤, 0.4~0.6이면 “판단 어려움”으로 표시합니다. 판정은 반올림 전 값으로 하고, 보여 주는 prob만 소수 셋째 자리로 반올림합니다.
돌려주는 것
소견마다 status가 evaluated이면 확률·문구·쓴 면·빠진 면, not_evaluated이면 이유와 필요한 면.
하지 않는 일
필요한 촬영면이 없을 때 낮은 확률로 채우지 않습니다. NaN이나 범위 밖 확률은 결과로 내지 않고 오류를 냅니다.
헷갈리기 쉬운 점
반월판은 axial·coronal만 씁니다. sagittal만 넣으면 반월판은 “판단하지 않음”으로 나옵니다. 학습 폴더의 원본 코드는 이때 sagittal 모델로 대신 답했지만, 성능이 낮아 뺀 것이므로 의도한 차이입니다.

class/knee/localization.py — 위치 표시

한 줄
ACL이 있는 대략적 위치 박스와, 모델이 참고한 영역 색칠을 만듭니다.
받는 것
슬라이스 한 장(0~1 회색), 또는 볼륨과 모델.
하는 일
YOLO 모델로 박스를 찾고, Grad-CAM으로 어디를 참고했는지 계산해 가장 강한 한 덩어리만 옅게 칠합니다. 최댓값의 5%보다 큰 반응만 칠하기 때문에, 반응이 한 점뿐인 CAM에서도 반응 없는 영역까지 칠하지 않습니다. 계산 도중 실패해도 걸어 둔 감시 장치(hook)를 반드시 뗍니다.
돌려주는 것
박스(0~1 비율 좌표, 못 찾으면 None), 색칠한 이미지와 “색칠했는지” 여부.
하지 않는 일
병변(파열) 위치를 알려 주지 않습니다. 반응이 없는 CAM에는 색칠하지 않고 원본을 그대로 돌려줍니다.
헷갈리기 쉬운 점
박스가 None인 것은 오류가 아니라 “못 찾았다”는 정상 결과입니다. 호출하는 쪽이 이 경우를 처리해야 합니다.

ACL 위치 안내를 점수와 분리하기

class/knee/screen_localization.py는 중복을 뺀 사용 목록의 가운데 한 장만 받아, 고정 SHA의 로컬 캐시 YOLO로 대략적 ACL 위치를 찾습니다. 다른 장·정답 박스로 대신하지 않습니다. 박스는 그 캡처의 0~1 좌표이며, 종횡비를 유지한 그림에 테두리만 그립니다. 원 좌표가 무한대·범위 밖이면 먼저 거절합니다.

서버의 KNEE_SCREEN_LOCALIZATION_ENABLED가 정확히 1일 때만 위치 모델을 호출합니다. 미설정·빈 값·0·잘못된 값은 disabled_by_policy로 보류합니다. 꺼짐이면 캐시 조회·모델 로드·탐지·그림 생성 모두 하지 않으며, 볼륨 점수와 해설·한 장 참고 열지도·뇌 분석은 유지합니다. 요청 데이터로 이 서버 설정을 바꿀 수 없습니다.

visualization.kind=anatomical_box는 별도 ACL 위치 모델의 참고 박스, grad_cam은 한 장 모델의 참고 열지도입니다. 위치가 없거나 오류·부분 입력·설정 꺼짐이면 kind=none과 고정 안내만 냅니다. 미검출은 정상이라는 뜻이 아닙니다. YOLO도 학습·선정 자료에 노출됐으며 화면 캡처의 해부학/병변 정확도를 검증한 결과가 아닙니다.

이 파일은 위치 안내만 담당하고 분류 입력·점수·보정·DB·NAS를 바꾸지 않습니다. 결과는 같은 화면 칸에 나타나며, 원본 영상/그림을 저장하지 않습니다. 운영에서 문제가 생기면 승인된 시작 스크립트의 -LocationOff로 위치만 보류하고 --expect-location-off로 점검합니다. 실제 설정 변경과 서버 재시작은 별도 실행 범위입니다.

POST /api/v1/knee/screen-analysis(routers/kneeScreenAnalysis.py, 검증·응답 class/knee/scroll_analysis.py, 모델 class/knee/acl_volume.py). 화면 /에서 부위 무릎 MRI·박스를 정한 뒤 넘기며 분석을 누르고 시상면 MRI 를 넘기면, 브라우저(assets/js/knee-scroll-capture.js)가 바뀐 장을 자동으로 모아(최소 10·권장 15·최대 20, 같은 화면은 원 화소 해시로 한 번만) 보냅니다.

수집 방식(capture_profile_v4): 브라우저가 지원하면 공유 영상에 새 프레임이 올 때마다 박스를 확인하고, 같은 그림이 0.1초 이상 유지될 때 한 장으로 채택합니다. 지원하지 않는 브라우저는 예전처럼 0.1초 간격으로 확인합니다(capture_profile_v4_interval). 새 장이 5초 동안 추가되지 않으면 화면에 "공유 대상과 수집 목록을 확인해 주세요" 안내를 띄우지만, 자동으로 다시 시작하거나 제출하지는 않습니다(정지한 화면일 수도 있음). 공유 종료·박스/해상도 변경·전체 120초는 창이 가려져 있어도 수집을 멈춥니다.

한계: 한 PC·한 Chrome에서 고정 시범 6케이스로 확인한 수집 개선이며(첫 시도 6/12 → 11/12), 다른 장치·브라우저·모바일 실제 공유에서의 효과는 확인하지 않았습니다. 장이 빠졌는지는 사용자가 수집 목록에서 확인해야 하며, 이 변경은 점수·진단 성능과 무관합니다.

  • 입력: multipart frames(PNG/JPEG 반복, 장별 1MiB·전체 16MiB·한 변 64~512px·모두 같은 크기), manifest(JSON: schema_version=1·plane=sagittal·image_scope·capture_intent=scroll|single·capture_profile_id·frames[{sequence,file_index,captured_at_ms}]), 선택 include_overlay. 모르는 필드는 400.
  • 장 수는 서버가 디코딩하고 같은 화소를 뺀 수로 정합니다. 넘기며 10~20장 → ACL 시상면 여러 장 모델(best_acl_combined 하나만 처음 쓸 때 불러옴). 9장 이하 422, 21장 이상 413. 넘기며 분석이 중복을 뺀 뒤 1장이어도 한 장 모델로 바꾸지 않고 422.
  • 한 장(capture_intent=single, 화면의 '선택 영역 분석'): 정확히 1장 → ACL 시상면 한 장 2D 모델(class/knee/single_image.py, 사용자 Colab 학습 반입본 v1, ResNet18·logit 1개). 응답 model_kind=single_2d·profile_id=knee_single_demo_v1, 점수는 raw 만(score_only·band=null·보정 미사용), 같은 logit 의 Grad-CAM(모델 입력 224×224 위), 한 장용 고정 해설. 모델 폴더는 서버 설정 KNEE_SINGLE_BUNDLE_DIR 로만 정하고(요청으로 경로를 받지 않음), 코드에 고정한 SHA-256 과 다르거나 설정이 없으면 503 model_single_not_ready(여러 장 모델로 대신하지 않음). 전처리는 학습 때와 같음: 회색 → 이미지별 min-max → 224 bilinear(antialias) → 3채널 → ImageNet 정규화. 근거(evidence): 검사 그룹 내부 holdout 181(데이터셋 ACL 중간 장 조건, AUROC ≠ 정확도)·약한 라벨·외부 확인 미실시·높은 쪽 오판 목표 미충족(판정에 안 씀)·독립 검증 아님.
  • 응답: 실제 모델 점수(acl.raw_score, 보정 전이면 score_kind=raw·decision=score_only), 별도 위치 모델의 ACL 참고 박스(허용·검출된 경우만)와 수집 순번, 결과 값으로 만든 고정 해설(생성형 AI 아님). 볼륨 Grad-CAM은 계산·표시하지 않습니다. 점수 모델의 판단 근거·파열 위치 안내가 아닙니다.
  • 자원: 본문은 파싱 전에 실제 바이트로 세어 한도를 넘으면 바로 413. 계산은 하나씩(진행 중이면 429), 시간 초과 504 뒤에도 그 계산이 끝날 때까지 429. 이미지는 저장하지 않으며 DB·NAS·학습 기록을 쓰지 않습니다.
  • 설정(선택): KNEE_SCREEN_ANALYSIS_ENABLED(기본 1), KNEE_SCREEN_ANALYSIS_TIMEOUT_S(기본 60), KNEE_SCROLL_DEVICE(기본 cpu), KNEE_SINGLE_BUNDLE_DIR(한 장 모델 폴더, 비우면 한 장 분석 503. 모델은 Git·공개 정적 폴더·NAS 웹 폴더에 두지 않음).
  • 비교 기준선(보정 v2): class/knee/score_reference.py. 서버 설정 KNEE_SINGLE_CALIBRATION_FILE·KNEE_VOLUME_REFERENCE_FILE 의 sidecar JSON 을 코드에 고정한 SHA 와 대조한 뒤에만 쓴다(형식·모델 SHA·입력 정책·범위 불일치 → raw 만, acl.reference_status 에 사유). 한 장: decision=reference_compared, acl.reference(데이터셋 기준 비교선·위/아래), acl.band(high/low/uncertain 참고구간). calibration 181 로 고정하고 이미 사용한 내부 test 181 로 버전별 감사 1회 확인(새 독립 시험 아님). 감사에서 보정 점수 표시는 미채택이라 점수는 raw 그대로. 적용: 시상면·영상 한 장 전체(데이터셋 가운데 장 조건이라고 가정, 서버가 확인하지 못함). 넘기며: '학습 노출 자료 기준선(탐색)'은 서버가 가운데 연속 15장 조건을 확인한 통제 시연에서만 쓰며, 일반 화면 공유에서는 확인할 수 없어 참고선을 생략한다(점수·해설은 유지, 위치 표시는 별도 설정). 해설은 0.5 같은 임의 기준으로 방향을 나누지 않으며 '의료 진단이 아님'을 항상 포함한다.

화면 캡처 한 장 분석 (API)

POST /api/v1/knee/screen-roi는 사용자가 화면 공유 중인 외부 뷰어에서 캡처한 이미지 한 장을 받습니다. 뇌 CT 화면 공유 분석(routers/brain.py)과 같은 자리에 있지만, 요청·응답 형식은 따로 정합니다(무릎은 부위·촬영면·이미지 범위를 함께 받음).

왜 대부분 “평가하지 않음”인가요? 무릎 분류 모델은 원래 촬영면별 슬라이스 묶음을 보고 판단하도록 만들어졌습니다. 한 장만 넣으면 돌아가지만 학습 조건과 달라서 믿을 만한지 따로 확인해야 하는데, 실험(2026-09-30) 결과 확인한 33개 조합이 모두 통과하지 못했습니다. 한 장의 점수는 슬라이스를 늘릴수록 좋아지고, 한 장일 때는 검사의 이상 여부와 거의 무관하거나 거꾸로 움직이는 경우도 있었습니다. 그래서 통과한 조합만 점수를 보이도록 “게이트 표”를 두었고, 지금 표는 비어 있습니다.

요청

  • multipart/form-data: image(PNG 또는 JPEG 한 장), body_part="knee", plane(axial·coronal·sagittal), image_scope(full_slice·roi_crop), 선택 include_overlay(true·false).
  • 필드가 빠지거나 두 번 들어오거나 모르는 필드·값이면 400. 파일이 5MiB를 넘으면 413, PNG/JPEG가 아니면 415, 읽을 수 없으면 422(빈 파일, 64px 미만, 움직이는 이미지, 한 가지 밝기뿐인 이미지 포함), 한 변 1024px 초과는 413.
  • 모든 오류 본문은 {request_id, code, message, retryable} 네 칸뿐이며, 올린 값·파일 이름·예외 원문·모델 저장소 이름을 넣지 않습니다.

응답 (HTTP 200은 “처리했다”는 뜻이지 “진단했다”는 뜻이 아님)

  • analysis_status: evaluated(세 소견 모두) · partially_evaluated · not_evaluated.
  • findings: abnormal·acl·meniscus마다 status가 evaluated 또는 not_evaluated. 평가하지 않은 소견은 prob·confidence_band·verdict가 모두 null이고 이유(reason)와 빠진 촬영면(missing_planes)이 적힙니다.
  • visualization: Grad-CAM(shown·no_activation·not_evaluated)과 ACL 위치 박스. 박스는 승인된 sagittal + 전체 슬라이스에서만 나오며 “해부학적 대략 위치, 파열 위치 아님”을 함께 적습니다.
  • notices(한 장 한계·학습용·전문가 상담·개인정보 확인·삭제 안내), evidence(승인 근거·성능), explanations(사람이 검수한 고정 설명), retention(서버가 이미지를 지웠다는 사실만), latency_ms, models_loaded.

POST /learning/roi-grade/knee: 학습자가 그린 박스(ROI)를 그 문제의 사람이 검수한 기준 ROI와 IoU로 비교해 채점합니다. 도형은 박스만 받습니다. 한 장짜리 문제는 그 한 장을, 여러 장(슬라이드) 문제는 서버가 정한 대표 슬라이스 한 장만 채점합니다(“ACL이 포함된 참고 영역 표시 연습”이며 파열 병변 탐지가 아닙니다). 기본은 꺼져 있고, 승인된 기준 ROI가 지금은 하나도 없어서 모든 문제가 “채점하지 않음”입니다.
받는 것
study_idx(필수, 무릎 MRI 문제), roi_type(box만 가능, 원 circle 등은 400으로 거절), 이미지 전체를 0~1로 본 박스 좌표(x,y,width,height, 이미지 안에 있어야 함). 슬라이드 문제는 여기에 slice_index(화면이 보여 준 슬라이스의 등록 배열 위치, 0부터, 필수, 없거나 형식이 틀리면 400)와 problem_token(문제를 열 때 서버가 준 쪽지)도 받습니다. 이미지, 영상 경로·해시, 기준 ID, 촬영면, 사용자 번호는 받지 않습니다(보내도 무시). 로그인은 학습자 세션 learner만 인정하고 관리자 세션 user는 인정하지 않습니다.
하는 일
① KNEE_ROI_GRADE_ENABLED=1인지 확인 → ② 세션 로그인(401)과 이메일 인증(403, D-033) 확인 → ③ study_idx가 활성 무릎 MRI 문제인지 확인(404) → ④ 박스 좌표 검사(박스만, 이미지 안, 400) → ⑤ 문제 이미지가 한 장인지 슬라이드인지 확인 → ⑥-a 한 장이면 reference_rois.py에서 승인된 기준 ROI를 찾아 IoU를 계산, ⑥-b 슬라이드면 kneeSliceGradeServices.py가 슬라이드 목록(경로 배열·목록 해시)을 검사하고 slide_references.py에서 승인된 대표 기준을 찾은 뒤, 토큰(서명·만료·사용자·문제·목록 버전·대표 번호·기준 버전)을 확인하고 대표 장일 때만 IoU를 계산(다른 장은 채점하지 않고 저장도 하지 않음). 규칙은 D-069: IoU 0.5 이상 정답, 0.2 이상 0.5 미만 부분정답, 그 미만 오답이며 규칙 버전(rule.version)을 응답에 적습니다. 판정은 512×512 격자에서 센 겹친 칸 수와 합친 칸 수(정수)로만 하고, 응답의 iou(실수)는 표시용입니다(그래서 표시가 0.5여도 절반에 한 칸 모자라면 부분정답일 수 있습니다). 채점되면 review_node에 사용자(세션), 문제, 판정을 저장하고 서버가 가진 문제 이미지 경로를 rn_image로 씁니다. 다음 무릎 MRI 문제(next)도 돌려줍니다.
돌려주는 것
graded, result, iou(표시용), overlap_px(격자 크기·겹친 칸 수·합친 칸 수), rule, user_roi_bbox, reference_bbox, reference(출처·버전), plane(기준 ROI에 적힌 서버 기록), notices, next, 저장 정보. 채점하지 않으면 graded=false이고 정답 정보는 비어 있으며 저장도 하지 않습니다. 사유(not_graded_reason)는 reference_not_approved(한 장 문제의 승인된 기준 없음), no_reference_for_slice(슬라이드에서 승인된 대표가 없거나 대표가 아닌 장), reference_ambiguous(승인이 둘 이상), token_invalid/token_expired/presentation_changed(제시 토큰 문제·유효 시간·문제가 바뀜), study_image_unavailable(문제 이미지를 확인할 수 없음), asset_changed(영상 확인 실패, NAS 연동 시) 중 하나입니다. 슬라이드 문제에서 채점되면 응답에 slice_index, rule_version, reference_basis=dataset_acl_region, clinical_validated=false가 붙습니다. 이 기능은 승인표가 비어 있어 아직 어떤 문제도 채점하지 않습니다.
하지 않는 일
AI 모델(YOLO 포함)로 기준 영역을 만들지 않습니다(D-071). 학습자가 올린 이미지를 받거나 NAS에 저장하지 않습니다(D-068). 병변 여부를 말하지 않으므로 has_abnormality, abnormality_bbox, classification 같은 뇌 API의 이상 소견 칸을 쓰지 않습니다. 뇌 채점의 재현율 조건도 쓰지 않아, 화면 전체를 크게 그려 정답이 되는 일이 없습니다.
헷갈리기 쉬운 점
기준 ROI를 표에 올리려면 출처, 버전, 검수자, 검수 시각, 촬영면, 0~1 좌표가 모두 있어야 합니다. 하나라도 빠지면 없는 것으로 봅니다. 그리고 이 서버의 학습자 로그인은 아직 세션을 만들지 않습니다(관리자 로그인만 session["user"]를 씁니다). 그래서 학습자 로그인이 idx와 email_verified를 세션에 넣어 주기 전에는 이 주소가 401을 돌려주는 것이 정상입니다. 화면 공유 분석(/api/v1/knee/screen-roi)과는 별개입니다.

routers/kneeLearning.py, templates/knee_learning.html, assets/js/knee-learning*.js, assets/css/knee-learning.css — 무릎 학습 화면 (대표 영상에 박스 그리기)

한 줄
GET /learn/knee: 대표 영상 한 장을 보고 ACL이 포함된 참고 영역에 사각형 박스를 그려 제출하면, 기존 채점 API(POST /learning/roi-grade/knee)의 결과를 보여 주고 다시 풀 수 있는 화면입니다. 메인 화면(/)의 무릎 AI 분석과는 별개의 학습 채점 흐름입니다.
두 가지 모드
?demo=1 시연: 합성 영상과 “시험용 응답”만 씁니다. 서버로 아무것도 보내지 않으며 실제 채점이 아닙니다(화면 위에 표시). ?study_idx=번호 실제 연결: GET /learning/knee/task로 문제를 열고 채점 API로 제출합니다. 상대 주소와 same-origin 쿠키 세션을 쓰므로 화면과 서버가 같은 Origin(주소·포트까지 같음)이어야 하며, CSRF·Origin 검증 정책은 팀장의 인증 설계 전까지 완성되지 않았습니다(이 화면이 막아 주지 않습니다).
화면이 하는 일
영상 표시, 박스 그리기·이동·크기 조절(마우스·손가락·방향키), 확대, 초기화, 제출, 결과 표시, 다시 풀기. 좌표는 “실제 영상이 그려진 상자”를 기준으로 0~1로 바꿉니다(확대·화면 크기·여백과 무관). 영상 밖으로는 박스를 만들 수 없고, 원 도형은 없습니다.
화면이 하지 않는 일
채점 계산, 기준 박스 보관, 정답 판정. 기준 박스는 채점된 뒤 서버 응답으로만 받아 그립니다. 박스·토큰·응답을 브라우저에 저장하지 않습니다.
GET /learning/knee/task
로그인한 학습자에게 knee_task(대표 슬라이스 번호, 영상 주소·크기, problem_token)를 줍니다. 승인된 대표가 없으면 사유만 줍니다. 정답 박스·진단·출처·검수자·내부 경로는 넣지 않고, Cache-Control: no-store로 보냅니다. 영상 주소·크기를 주는 “영상 공급자”는 아직 연결되지 않아(팀장·NAS 작업 대기) 기본은 닫혀 있습니다(503). 영상을 공급받는 동안 문제 목록이나 승인 기준이 바뀌면 섞어서 내려주지 않고 409로 닫습니다(공급과 토큰 발급은 같은 snapshot). 응답의 presentation_id는 “같은 영상인가”를 비교하는 불투명한 값(경로·해시를 드러내지 않음)입니다.
문제 열기 실패와 박스 초안
문제를 열지 못하면(통신·서버·로그인·영상 오류) 영상 자리에 항상 다시 시도 버튼이 남습니다(결과 카드가 숨겨져도 사라지지 않음). 박스 초안은 메모리에 보관하며, 다시 연 영상이 같은 영상이면 그대로 돌려주고, 대표 영상이 바뀌었거나 같은지 확인할 수 없으면 자동으로 옮기지 않고 변경 안내와 함께 “새로 그리기 / 이전 박스를 이 영상에 사용(직접 확인)” 중에서 고르게 합니다.
제출 결과를 못 받았을 때
통신이 끊겨 응답을 받지 못하면 서버가 이미 처리했는지 알 수 없습니다. 화면은 “저장되지 않았다”고 단정하지 않고, 다시 제출하면 기록이 한 번 더 남을 수 있다고 알립니다. 토큰 재사용은 별도 학습 시도를 허용하는 정책이며 중복 제거 키가 아닙니다(운영 이력 연결 때 별도 계약이 필요).
결과 표현
“기준 영역과 일치 / 일부 일치 / 차이 있음”과 “영역 겹침(IoU)”만 씁니다. 채점하지 않은 응답(graded=false)은 정답·오답으로 보이지 않게 사유만 안내하고 박스를 보존합니다. 통신이 실패해도 박스를 보존해 다시 제출할 수 있습니다. 항상 “데이터셋 라벨 기준, 임상 검증 아님”을 보여 줍니다.

학습자 로그인 칸 (/learn/knee)
문제를 열 때 서버가 401(로그인 필요)로 답하면 화면에 로그인 칸이 나타납니다. 기존 POST /login만 부르고(같은 Origin 쿠키), 성공하면 문제를 다시 엽니다(박스 초안 보존 규칙 그대로). 실패 문구는 상태 코드만 보고 고르며 서버 응답 본문은 읽지 않습니다(공용 로그인 응답에 개발용 필드가 섞여 있어 화면·기록에 비밀번호가 나오지 않게). 비밀번호 칸은 요청이 끝나거나 실패하면 비우고, 입력칸에 name 속성이 없어 주소·저장소에 남지 않습니다(브라우저 개발자 도구의 네트워크 탭·서버 쪽에는 요청이 보일 수 있습니다). 문제를 열 때뿐 아니라 제출이 401(세션 끊김)일 때도 영상·박스를 그대로 둔 채 같은 페이지에서 로그인할 수 있으며, 성공하면 같은 영상이면 박스가 돌아오고 대표가 바뀌었으면 변경 안내·직접 확인 뒤에만 제출됩니다.
이메일 인증이 아닙니다
발표 한정 관리자 승인 예외: 관리자(팀)가 직접 만든 활성 회원이 로그인하면 승인된 학습자로 봅니다. 세션 값 email_verified=True는 이메일 인증 완료가 아니라 관리자 승인 표시입니다(DECISIONS 2026-10-13, AUTH_SESSION_CONTRACT 7장). 발표 후 서비스를 이어가면 D-033 원문으로 되돌립니다. 공용 로그인 응답의 비밀번호 기록 위험(LOGIN-019-01)은 별도 수정 승인안으로 남아 있습니다.
영상 공급 (NAS 또는 서버 폴더 — 둘 중 하나만 설정)
서버가 영상을 한 번 읽은 바이트로 SHA-256과 PNG 치수를 승인 기준과 대조한 뒤 그 바이트를 그대로 로그인한 학습자에게 GET /learning/knee/image/{study_idx}/{presentation_id}로 보여 줍니다(no-store, 파일 이름·다운로드 헤더 없음). 주소의 식별값이 현재 승인된 대표·영상과 다르면 404입니다. NAS 공급원(KNEE_NAS_IMAGE_BASE_URL, https만)은 리다이렉트를 따르지 않고 시간·크기(8 MiB)를 제한하며, 검증한 바이트를 메모리에 10분만 둡니다. 폴더 공급원(KNEE_IMAGE_DIR)은 폴더 밖·링크·정션·드라이브·대체 스트림·정적 공개 폴더를 거절합니다. 정확히 하나만 설정해야 하며, 둘 다 설정하거나 둘 다 비우거나 설정 값이 잘못되면(다른 공급원으로 넘어가지 않고) 닫힙니다(제시 503). 폴더 공급원은 정적 공개 폴더(assets/·templates/) 안이거나 그것을 포함하는 상위 폴더이면 설정 자체를 거절하고, 실제로 여는 파일이 그 안이어도 거절합니다.
제출 때도 검증
제시(task), 영상 주소, 제출 모두 같은 검사를 합니다. 제출 때는 grade_slide의 asset_verifier로 대표 영상을 다시 대조해, 내용·치수가 다르면 asset_changed, 가져오지 못하면 study_image_unavailable로 미채점·저장 0건입니다. 검증을 건너뛰는 경로는 없습니다: 공급원이 없거나 둘이거나 잘못된 설정이면 유효한 토큰으로 제출해도 미채점·저장 0건이며, 검증 생략은 시험이 명시로 주입할 때만 가능합니다(운영 코드에는 없음). 영상을 읽는 동안(느린 NAS·디스크) 승인·문제가 바뀌면 영상 주소는 409, 제출은 presentation_changed 미채점·저장 0건으로 닫습니다(이 단계는 읽는 동안의 변경을 닫는 것이며 DB 트랜잭션 원자성까지 보장하지는 않습니다). 승인 기준에는 영상 치수(image_width/height)가 필수이며 읽은 PNG 치수와 같아야 합니다.
이 방식의 한계

서버 밖에서 사람이 돌리는 도구입니다(서버 코드는 불러오지 않음). 로컬 KneeMRI 볼륨에서 후보 슬라이스(roiZ + roiDepth // 2)와 24장 슬라이드, 해시·치수·정규화 박스, 검수용 오프라인 HTML 시트를 만듭니다. 축 [z, y, x]·0 기반·전치/회전/뒤집기 없음·볼륨 전체 백분위 창을 모두 명시하고, 추출 PNG와 박스가 같은 변환임을 비대칭 합성 볼륨으로 시험합니다. 후보만 만들고 승인하지 않으며 승인표·DB·NAS를 건드리지 않습니다. 검수자 3명의 결과(JSON)는 일치 여부만 보고합니다. 원본 pickle은 --trusted-local을 명시한 신뢰하는 로컬 자료만 읽고(numpy 배열만 허용), 환자 연결키·진단 라벨(PRIVATE_provenance.json)은 기본으로 만들지 않고, --private-dir(공유 출력 폴더의 바깥)을 명시할 때만 그곳에 만듭니다(안쪽·같은 폴더·상위 폴더는 거절, 공유 폴더 전체에 연결 정보가 없음을 시험으로 확인).
저장은 기존 review_node 그대로
채점이 되면 본인 회원·문제·대표 경로·서버 결과 한 줄이 저장됩니다. 이것은 사후 영상·박스·기준을 재현하거나 최근 3회/30일 정리·탈퇴 삭제를 구현한 것이 아닙니다(새 이력 구조는 미구현이며, 발표 최소 시연에서 제외·연기할지는 사용자 확인 대기). 관리자 리뷰 화면에서 이 경로의 이미지가 보이는지는 확인하지 않았습니다.
